# serial-commit

ステージング済みの変更を元にコミットを作るスキル。

## なぜこのスキルがあるのか

ユーザーは:
- 自分で `git add` してステージした内容を、言葉での依頼だけでコミットしたい
- コミットの author date を連続した日付で並べたい(履歴の間を埋めるように、意図的に日付を遡って入れる)というワークフローを持っている

そのため、このスキルは「ステージ済みの変更からコミットメッセージを考えて作る」「直前のコミット日付を見て、必要なら author date を上書きするか聞く」という2つの責務を持つ。

## 全体フロー

1. ステージされた変更を確認する
2. リポジトリの慣習に合うコミットメッセージを考える
3. 直前のコミットの author date を確認し、必要に応じてユーザーに author date を上書きするか聞く
4. コミットを実行する

## 詳細

### 1. ステージング内容の確認

```bash
git status --short
git diff --cached --stat
git diff --cached
```

**何もステージされていない場合は停止する。** その旨ユーザーに伝え、`git add` を勝手に実行しない — ユーザーがステージしていないファイルは意図的に除外している可能性が高いから。

### 2. コミットメッセージを考える

`git log --oneline -10` で過去のコミットを確認し、リポジトリの慣習に合わせる。例えばこのリポジトリでは:

- 日本語で短く
- 「○○を追加」「○○を更新」「○○を修正」のような語尾
- 複数の変更を1コミットにまとめる場合は `|` で区切る(例: `レジダッシュボードを DB 連携に変更 | 決済処理アクションを追加`)

ステージされた diff の中身を見て、「何が」「なぜ」変わったかが伝わる文を作る。

### 3. 直前のコミットの author date を確認

```bash
git log -1 --format=%ad --date=format:%Y-%m-%d
```

得られた日付と今日の日付を比べて、以下のように分岐する。

| 直前のコミット日 | アクション |
|---|---|
| 今日 | そのまま普通にコミット(確認なし) |
| 昨日 | そのまま普通にコミット(確認なし) |
| 2日以上前 | author date を上書きするかユーザーに確認 |

### 4. author date 上書きの確認(2日以上前の場合のみ)

次のように聞く:

> 直前のコミットは `YYYY-MM-DD` です。今回のコミットの author date を `YYYY-MM-DD の翌日` に設定しますか? (yes/no)

- **yes** → `GIT_AUTHOR_DATE` を設定してコミット
- **no** → そのまま普通にコミット

時刻部分は `12:00:00` のような中庸な値で良い。`git log` の Date 行に表示されるのは AuthorDate なので、`GIT_AUTHOR_DATE` だけ設定すれば履歴上の見た目は揃う(`GIT_COMMITTER_DATE` は設定しなくて良い)。

### 5. コミット実行

メッセージは HEREDOC で渡す(改行や引用符の取り扱いを安全にするため):

```bash
git commit -m "$(cat <<'EOF'
コミットメッセージ
EOF
)"
```

author date を上書きする場合は先頭に環境変数を付ける:

```bash
GIT_AUTHOR_DATE='2026-05-06 12:00:00' git commit -m "$(cat <<'EOF'
コミットメッセージ
EOF
)"
```

コミット後に `git log -1 --oneline` で結果を確認し、ユーザーに報告する。

## 守ること

- `Co-Authored-By` トレーラーは**付けない**。
- `git add` を勝手に実行しない。ユーザーが自分でステージしている前提。
- 既存コミットを `--amend` で書き換えず、必ず新しいコミットを作る。pre-commit フックが失敗したら原因を直して新規コミット。
- `--no-verify` 等でフックをスキップしない。
- `git push` は明示的に頼まれない限り実行しない。
