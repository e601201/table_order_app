# Staff の削除は物理削除（ライフサイクルを持たない）

スタッフ管理画面はスタッフを物理削除（`destroy`）し、有効/無効ステータスや論理削除（削除済）といったライフサイクルを `Staff` モデルに持たせない。デザイン comp（`mobileOrder.pen` の「ユーザー管理」）には「アクティブ/削除済」ステータス・統計・フィルタが描かれているが、POC のスコープとして意図的に不採用とした。

## Considered Options

- **有効/無効ステータス + 論理削除** — 却下。`status` / `deleted_at` カラム、一覧のフィルタ、ログイン拒否ロジックが必要で POC には過剰。`Order` は `Staff` を参照しない（誰が提供したか・会計したかを持たない）ため、物理削除しても参照整合の問題は生じない。
- **物理削除 + 「管理者 ≥ 1」不変条件** — 採用。最後の管理者の削除・降格、および自分自身の削除をサーバー側で禁止し、管理画面からのロックアウトを防ぐ。

## Consequences

- `Staff` に `status` / `deleted_at` カラムは追加しない。
- 監査・復元・休眠アカウントが必要になったら、`status` カラム追加を別 ADR に委ねる。
- 「管理者 ≥ 1」は `destroy` と `update`（ロール降格）の両方で検証する。一覧のデザインにあった「削除済」統計・「アクティブ」フィルタは、status カラムを持たないため実装しない。
