# 決済方法マスタ（DB 化 `PaymentMethod` ＋ `/admin/settings`、`Order` へは FK ではなく会計時の名前スナップショット）

ハードコードされた決済方法（`cash` / `credit_card`）を DB マスタ **`PaymentMethod`（name ＋ 有効フラグ）** に置き換え、Admin が `/admin/settings`（サイドバー「設定」、「運営管理」セクションへ移動）でインラインに追加・改名・トグル・削除できるようにする。`Order.payment_method` は **FK ではなく、会計（`Settlement`）時に方法の名前をそのままスナップショットする文字列**のまま — マスタを後から改名・削除しても会計済みの歴史は変わらない。不変条件は「**有効な決済方法が最低1つ**」のみ（現金の特別扱いなし）。無効化・削除済みの方法での会計は**拒否**する（現行の「不正値を黙って `cash` に読み替える」フォールバックは廃止）。正準名は **決済方法**（CONTEXT.md で確定 — 「支払い」は客向けコピー専用、「決済」は複合語専用の既存三分法に適合）。

背景: 決済方法はこれまで `cashier_controller.rb` に `%w[cash credit_card]` として焼き込まれ、「PayPay 始めました」がデプロイを要する状態だった — メニューが ADR-0004 以前に抱えていたのと同じ不便。マスタ化を安全にする決定的な事実は、**方法にコード上の振る舞いが一切紐付いていない**こと（お釣り計算・預かり金額入力は存在せず、方法は会計時に記録される純粋なラベル）。振る舞いがないからこそ Admin の自由追加が壊すロジックがない。もしお釣り計算があれば固定カタログを採っていた。

## Considered Options

### 設定の形

- **マスタ CRUD（採用）** — 現実の運用シナリオは「PayPay 導入」（追加）と「端末故障で今日だけクレジット停止」（一時停止）。前者をデプロイなしにするには DB 化しかない。ADR-0004（メニュー DB 化）と同じ動機・同じ帰結。
- **固定カタログ＋有効/無効トグルのみ（却下）** — 最小だが、新方法の追加が毎回デプロイになり ADR-0004 以前の不便を再生産する。

### `Order` との接続

- **名前スナップショット（採用）** — `Order.payment_method` は既に文字列カラム。会計時に方法名を焼き込めば、改名・削除が過去の注文の表示を書き換えない。`Checkout` で `Line` が `MenuItem` の name / price を焼き込むのと同一の哲学 — 「確定した歴史はマスタの後日変更に影響されない」をドメイン全体で一貫させる。
- **FK 参照（却下）** — 正規化としては正統だが、改名が会計済み注文の表示を遡って書き換える（「現金」で払った記録が改名後の名前に化ける）。削除には restrict か soft delete が必要になり、ADR-0003 流のハードデリートとも衝突する。**後から来た読者が「FK がない、直そう」と思う典型ポイントなので、本 ADR がその防波堤。**

### ライフサイクル

- **有効/無効トグル＋物理削除の2段構え（採用）** — 「端末が直ったら戻す」（一時停止）と「契約解除でもう戻さない」（恒久撤去）は運用上別の行為。トグルだけだと OFF 行が「今日だけ停止」なのか「2年前にやめた」なのか区別できず一覧が墓場になる。`MenuItem` の `Suspended`／物理削除と同型で、新パターンを増やさない。削除の安全性はスナップショットが担保。
- **トグルのみ（却下）** — 上記の墓場化。

### 全滅ガード

- **「有効な方法が最低1つ」をモデルバリデーションで強制（採用）** — どの手段でも金を受け取れないレストランは意味のある営業状態ではなく設定事故。意味のない状態は表現できなくてよい。最後の有効な1行は無効化も削除も拒否。
- **ゼロを許しレジ側にエラー状態を用意（却下）** — 事故でしか到達しない画面の設計・実装・テストのコストに見合わない。
- **現金を削除不可の固定行に（却下）** — キャッシュレス専門店は実在する正当な営業形態。ガードは不変条件1本にし、どれを残すかは Admin の自由。

### 会計時の不正値（無効化との競合）

- **拒否して会計画面へ差し戻し（採用）** — レジが画面を開いた後に Admin が方法を無効化する競合は、マスタ化で正当な経路になる。`payment_method` は会計の恒久スナップショットであり、PayPay で受けた金を黙って「現金」と記録すればレジ締めで現金が合わなくなる — 会計記録が嘘をつくのはこのドメイン最悪の failure mode。差し戻しは `close_order` の `redirect_to ..., alert:` と同じ既存の流儀。
- **フォールバック（現行踏襲、却下）** — 現行の `cash` 読み替えが無害だったのは選択肢が2つ固定で UI から不正値が来ようがなかったから。前提が変わるので設計も変える。

### 並び順

- **並び替え機能なし・登録順（採用）** — レジの選択肢は現実的に4〜5個で、並びが業務効率に効かない。seed で 現金 → クレジットカード を入れて現行の並びを維持し、新方法は末尾に付く（老舗が先頭・昨日始めた PayPay が末尾、は運用感覚とも一致）。必要になれば `position` 列1本の追加変更で足せる（可逆）。
- **`position` ＋並び替え UI（却下）** — 2フィールドのマスタに対して過剰装備。

### 既存データ

- **一括移行（採用）** — マイグレーションで `cash`→`現金`、`credit_card`→`クレジットカード` に UPDATE。以後カラムは常に「表示名がそのまま入っている」単一意味論になり、フロントのスラッグ→表示名マッピング（`PaymentComplete.tsx` / `OrderDetail.tsx`）は削除できる。値2種類・POC データの今が最小コスト。
- **二重意味論（旧行スラッグ・新行名前、却下）** — 「名前のスナップショットである。ただし歴史的例外を除く」という但し書きを全読者に永久に背負わせ、CONTEXT.md の定義とコードが一致しなくなる。

### 画面の形

- **`/admin/settings` 1ページ・インライン操作（採用）** — `PaymentMethod` は実質2フィールドで、専用 New/Edit ページを立てる厚みがない。行の追加・改名・トグル・削除をページ内で完結させる（ADR-0011 の「重いフォームを再送しない軽量オペ」と同じ性質）。サイドバー「設定」を有効化し「分析」→「運営管理」セクションへ移す。将来の設定項目はセクション追加で受ける。
- **独立リソースページ（`staffs` / `menu_items` 同型、却下）** — 2フィールドに index / new / edit の3ページは過剰。「設定」項目も空のまま残ってしまう。

## Consequences

- 新テーブル `payment_methods`: `name`（string, NOT NULL, 生存行内で一意）、`enabled`（boolean, NOT NULL, default true）。seed は 現金・クレジットカード（ともに有効）。
- モデルバリデーション: name 必須・一意、「有効な行が最低1つ」（最後の有効行の無効化・削除を拒否）。
- `cashier#process_payment`: `permitted_payment_method` の `cash` フォールバックを廃止し、**有効な `PaymentMethod` の name と一致しなければ会計を拒否**して会計画面へ alert 付きで差し戻す。
- レジの会計画面（`PaymentConfirm`）: 選択肢を有効な決済方法から動的に描画。デフォルト選択は先頭（= 現金相当）。
- データ移行: 既存 `orders.payment_method` の `cash`→`現金`、`credit_card`→`クレジットカード`。フロント2箇所のラベルマッピングを削除し、スナップショット文字列をそのまま表示。
- スタッフ画面のラベルは正準名「決済方法」へ寄せる（Admin `OrderDetail` の「支払い方法」など）。客の目に入るコピーのみ「お支払い方法」を許容（`Served` の 提供済み/受取済み と同じ型）。
- `/admin/orders` は閲覧専用のまま（ADR-0005 不変）。決済方法の管理は Admin 専有。

## 非ゴール

税率の設定化（軽減税率 8%/10% と総額表示の論点ごと別セッションに委ねる — 一律 `TAX_RATE` を設定可能にすると誤ったモデルを固定するため意図的に外した）／店舗情報（ADR-0005 の「Store 概念なし」維持）／カテゴリ管理／並び替え（`position`）／方法ごとの振る舞い（お釣り計算・決済端末連携）／客への決済方法選択の露出（選ぶのはレジのみ、という現行境界は不変）。
