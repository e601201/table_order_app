# 未払い注文の「打ち切り」は payment 軸の第2終端（`Unpaid → Paid | Closed`）

スタッフ起点で未払い注文を支払いなしで閉じる行為を **打ち切り（Close）** として導入する。payment 軸を二股終端 `Unpaid → Paid | Closed` に拡張し（`closed_at` タイムスタンプが `paid_at` と排他）、kitchen 軸には**触れない** — 注文は止まっていた場所で凍結する。打ち切りには4値固定の理由コード（`no_show` / `out_of_stock` / `customer_request` / `walkout`）を必須で添える。actor は **Cashier のみ**（レジ surface から）。打ち切りは **reopen（打ち切り解除）** で `Unpaid` に戻せる。客向けには LINE 注文履歴の「キャンセル」バッジ1種のみで、LINE 通知は送らない。

背景: キャンセル概念は ADR-0005・ADR-0009 で2度意図的に先送りしてきた。ADR-0009 の手渡し＝会計統合により、no-show のテイクアウトが `Ready + Unpaid` で滞留する穴が最も尖った形で残った — レジキューは当日スコープなので翌日には黙って消えるが、DB には未終端の行が残り、客の LINE 履歴には「提供待ち」が永遠に表示され続ける。品切れ・客の取り消し依頼・未払い離店（食い逃げ）にも、注文を閉じる手段が存在しなかった。

## Considered Options

### 状態モデル

- **payment 軸の第2終端（採用）** — 「この注文はもう支払われない」という事実の置き場所として意味が合い、kitchen 軸の凍結が3シナリオすべてで正直な歴史になる: no-show は `Ready` で凍結（料理は実際できていた）、walkout は `Served` で凍結（実際渡して食べられた）、品切れは `Pending` / `In progress` で凍結（作っていない）。既存キューは全て `paid_at: nil` でフィルタしているため `closed_at: nil` を足すだけ。
- **kitchen 軸に `cancelled` 状態を追加（却下）** — walkout で終端 `Served` からの遷移となり歴史を上書きする。調理の進捗という軸の意味に合わない出来事を混ぜることになる。
- **第3の軸（disposition: active / closed）（却下）** — 機能的には同じだが、`Paid + closed`（=返金）という組合せ空間を不要に開く。返金はスコープ外。

### 概念の数と正準名

- **1概念 + 理由コード（採用）** — no-show（廃棄）・品切れ（供給失敗）・取り下げ・未収は業務上の意味こそ違うが、状態機械上は同一の出来事（「もう支払われない、全キューから外す」）。違いは「なぜ」だけなので、状態を増やさず必須 enum で記録する。スタッフによる注文入力がこのシステムに存在しないため「スタッフ入力ミス」はあり得ず、誤注文は常に `customer_request` に吸収される。
- **取消 / 未収の2概念（却下）** — 状態機械への影響が同一のものを分けても複雑さしか増えない。
- **名前「キャンセル / Cancelled」（却下）** — 提供済み・消費済みの walkout を「なかったことに」と呼ぶのは、ADR-0009 で「表示だけ変える案」を却下したのと同種の言葉の嘘。
- **名前「ボイド / Void」（却下）** — 請求業界では void（債権が元々ない）と uncollectible（回収断念）を区別しており、1概念への統合と半分ズレる。
- **名前「打ち切り / Closed」（採用）** — `Settlement`（支払い**あり**で閉じる）の鏡像として、支払い**なし**で閉じる。3理由すべてで正直。

### actor

- **Cashier のみ（採用）** — payment 軸の両終端（`Paid` / `Closed`）をレジだけが書く、という一行で軸所有権が説明できる。品切れはキッチンから口頭でレジへ伝え、レジが打ち切る（客への謝罪・代替提案もどのみちカウンターで起きる）。
- **Kitchen にも許可（却下）** — 発見地点のエルゴノミクスは良いが、ADR-0009（レジ→kitchen 軸）と逆方向の第2の軸越えが生まれ、軸所有権の物語が薄まる。
- **`/admin/orders` に打ち切り操作（却下）** — ADR-0005（閲覧専用）の改訂が必要になる上、`Admin` はスイッチャーでレジ surface に入れるため専用の口は不要。

### reopen（打ち切り解除）

- **可・Cashier の単純逆操作（採用）** — 「no_show で打ち切った直後に客が現れる」は最も高頻度の解決シナリオ。`closed_at` / 理由をクリアして `Unpaid` に戻すと、凍結していた kitchen 軸のまま元のキューに再出現し、通常の会計で `Served + Paid` にできる。「`Closed` は終端」は「そこから先に進むものはない」という意味で保たれる — reopen は進行ではなく早すぎた判断の訂正。
- **不可（完全終端）（却下）** — 上記シナリオで「もう一度注文してもらう」しかなくなり、既に作った料理と新しい `Order` 行の二重化というより大きな嘘を招く。

## Consequences

- `orders` に `closed_at`（timestamp）と `closure_reason`（4値 enum）が増える。不変条件: `paid_at` と `closed_at` は排他、`closure_reason` は `closed_at` と運命を共にする。
- ガードは **Unpaid 限定 + order type 構造整合のみ**（`no_show` は Takeout 限定、`walkout` は In-store 限定）。kitchen 状態 × reason の整合は強制しない（現場の判断領域）。
- 打ち切られた注文は**全作業キューから消える**: キッチン盤面（当日4レーン）と `awaiting_payment` / `for_cashier_today` が `closed_at: nil` を要求するようになる。
- レジ surface には (1) キュー外の未払い注文（品切れ対象の `Pending` 等）に届く導線と、(2) 当日の Closed 一覧（reopen の到達経路）が必要になる。
- `OrderClosed` イベントを定義するが**購読者ゼロ**（In-store の `OrderReady` と同じ「誰も観測しない」パターン）。LINE 通知は送らない — 将来の品切れ通知（店に向かう客を止める）は購読者を足すだけで実現でき、状態機械には触れない。reopen はイベントを発生させない。
- 客向け表示: 「キャンセル」バッジ1種（理由を問わず）は Takeout の注文履歴に出す。嘘をつく唯一の組合せ（walkout）は In-store 限定。**当初の根拠「In-store の客に履歴 surface が存在しないため客の目に触れない」は ADR-0012 で改訂**され、現在の根拠は「In-store 客の surface（注文状況 `/order/status`）が会計軸を描かない — walkout は調理軸 `Served` のまま『提供済み』と表示し、提供前クローズは中立文言にする」。いずれにせよ「キャンセル」が嘘で客の目に触れることはない。スタッフ面は「打ち切り」。
- 指標: 売上・平均注文単価・7日トレンドは paid 基準のため構造的に無風。**注文数 KPI と人気 Top5（placed 基準）には Closed を含めたまま**とする — `no_show` / `walkout` / `out_of_stock` は実在した需要であり、除外するとむしろ需要指標が嘘になる。
- `/admin/orders` は閲覧専用のまま（ADR-0005 不変）、Closed バッジ + 理由を表示する。
- 客起点のセルフキャンセル・返金（`Paid` の取り消し）は引き続きスコープ外。
