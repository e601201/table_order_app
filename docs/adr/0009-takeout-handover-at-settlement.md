# テイクアウトの手渡しは会計と同一アクション（`Ready` から `Served + Paid` へ同時遷移）

`Takeout` の `Order` は、レジの `Settlement`（会計）が**手渡しを兼ねる**。`Ready` のテイクアウト注文をレジが会計すると、1アクションで `Served`（kitchen 軸）と `Paid`（payment 軸）に同時遷移する。キッチン盤面からテイクアウトを `Served` に進めることは**サーバー側で禁止**し、テイクアウトのキッチンの終点は `Ready`（`OrderReady` で客を呼び出すところまで）とする。客向け表示では、テイクアウトの `Served` を**「受取済み」**と表記する（スタッフ面は order type を問わず「提供済み」のまま）。

背景: テイクアウトのカウンターでは「商品を渡す」と「会計する」が物理的に同一瞬間に起きる（注文完了画面の案内も「お受け取りの際にレジでお支払い」）。従来は ADR-0001 の軸独立に従い、キッチン盤面で「提供済み」をタップしてからレジで会計する**2タップ運用**だったが、これは実態と合わず、注文履歴に「商品を持っているのに提供待ち」「受け取っていないのに提供済み」のような嘘の状態が見える余地を残していた。

## Considered Options

### 状態をどう変えるか

- **状態遷移ごと統合（採用）** — レジの会計が `Ready → Served + Paid` を同一トランザクションで進める。「受取済み」の表示と実際の受け取りが常に一致し、スタッフは1タップで済む。代償として ADR-0001 の「レジは kitchen 軸に触れない」にテイクアウトだけ意図的な例外を作る。
- **表示だけ変える（却下）** — 状態機械と2タップ運用は維持し、履歴の表示のみ `paid_at` で「受取済み」に切り替える。コードは最小だが、会計処理が遅れると「商品を持っているのに提供待ち」のズレが生まれ、「受取済み＝受け取った」という言葉が嘘をつく。
- **キッチンの「提供済み」タップを残したまま会計でも遷移（却下）** — 会計を経ない `Served + Unpaid` のテイクアウトが作れてしまい、「受取済み＝支払い完了時」の不変条件が壊れる。POC の運用に「先に渡して後で払う」例外は存在しない。

### レジのガードとキューの形

- **order type で前提を分ける（採用）** — 会計待ちキュー: In-store は `Served + Unpaid`（従来どおり）、Takeout は `Ready + Unpaid`。会計ガード: In-store は `served?` 必須、Takeout は `ready?` 必須。旧フローで作られた `Served + Unpaid` のテイクアウト行はリセット容認（#33 と同方針でレガシー救済分岐を入れない）。
- **Takeout は `ready?` / `served?` の両方を許す（却下）** — 既存データもそのまま会計できるが、「テイクアウトの `Served` は `Settlement` の結果でしか生まれない」という新ルールに例外が残り続ける。

## Consequences

- **ADR-0001 の軸独立に意図的な例外**ができる: テイクアウトに限り、レジが kitchen 軸の最終遷移を書く。両軸が別々に進む原則は In-store では不変。
- キッチン盤面: テイクアウトのカードは `Ready` 止まり。`kitchen#update_order_status` はテイクアウトの `served` 指定を拒否し（サーバー側が境界）、盤面 UI もテイクアウトには「提供済み」ボタンを出さない。
- レジ: `awaiting_payment` / `for_cashier_today` 相当のスコープと会計ガードが order type 分岐になる。`OrderReady` がテイクアウトのキュー進入シグナル（In-store は従来どおり `OrderServed`）。
- `OrderServed` はテイクアウトではレジ自身の `Settlement` が発生させる。会計時に LINE への追加通知は**送らない**（呼び出しは `OrderReady` で済んでいる。サービスメッセージの残送信回数も温存）。
- 客向けコピー: 注文履歴のテイクアウト終端は「受取済み」。`orderStatus.ts` の正準コピー（スタッフ面の「提供済み」）は不変で、客向けの言い分けとして1箇所だけ定義を足す（第3の表記揺れは作らない）。
- 来店しないテイクアウト客（no-show）は `Ready + Unpaid` で残り続けるが、キャンセル概念は引き続き持たない（ADR-0005 踏襲。従来も `Served + Unpaid` で残った — 問題の位置が変わっただけで悪化はしない）。
- 用語集の `Kitchen` / `Cashier` / `Order type` / `Served` / `OrderServed` / Language 冒頭を本決定に合わせて更新済み。
