# 会計は来店を終える — In-store 来店境界の二本立て

In-store の来店（`来店` / Visit — CONTEXT.md に新規定義）の境界を二本立てにする。従来の Welcome 再入場（運用上の「新しい来店の宣言」）に加え、**会計終端 — session の全 placed `Order` が payment 軸の終端に達し、かつ少なくとも1件が `Paid`** — を第2の境界として導入する。境界の発火で `session[:placed_order_ids]` と `Cart` を両方クリアし、`table_number` は残す（タブレットは卓に物理固定）。加えて `注文状況` の読み出し時に session の id 配列を当日分へ刈り込み、CookieOverflow を抑える。

背景はイシュー #55（PR #54 max code-review 指摘 #1 / CONFIRMED）。ADR-0012 の `session[:placed_order_ids]` はリセット経路が Welcome 入場1本しかなく、(1) スタッフが Welcome を経由せず席を使い回すと次客に前客の注文番号・品名・数量が漏れる、(2) cookie セッションの id 配列が刈り込まれず理論上 4KB を超え得る、(3) 同一客の Welcome 再通過で自分の進行中注文も消える、の3懸念があった。根本原因は In-store の `Customer` が identity を持たず「来店の終わり」を告げるイベントが無いこと — だが後会計フローでは **`Settlement` が構造的に来店の最終行為**であり、ドメインに既にある境界を使える。漏れ(1)と消失(3)は境界の問題、肥大(2)は保存先の問題で、両者は直交する（保存先をサーバに移しても境界イベントが無い問題は1ミリも動かない）。

## Considered Options

### 来店の第2境界
- **会計終端を追加（採用）** — 前客が普通に会計して退店した後の漏れ（最頻経路）を、スタッフの追加操作ゼロで塞ぐ。ドメイン的にも「会計＝来店の最終行為」の写しで自然。
- **現状維持＋ドキュメント明記（却下）** — CONFIRMED 指摘に対して挙動が何も変わらない。
- **Visit エンティティ導入（却下）** — サーバ側に Visit モデルを立てても「いつ visit が終わるか」という境界イベントの問題は storage と直交して残る。POC には過重。
- **アイドルタイムアウト（却下）** — 食事中は無操作が長い業態なのでタイムアウトを長く取らざるを得ず、席の回転が速いほど保護が弱くなる（逆相関）。

### 会計終端の条件
- **全 Order 終端 かつ ≥1 `Paid`（採用）** — ドメイン文は「**会計（`Settlement`）は来店を終える。打ち切りは終えない**」。客の唯一の注文が `out_of_stock` で打ち切られた場合、客はまだ席にいて代替注文をするはず — 中立文言「ご用意できませんでした」は表示され続ける。`Paid` と `Closed` の混在は「何かしら払って退店」なのでリセットする。
- **全 Order 終端のみ（却下）** — 規則は最も単純だが、全打ち切りの瞬間に中立文言が次のポーリングで無言で消える。ADR-0012 が「客の注文が無言で消えて『あれ？』となる」として却下した挙動（Closed 一律ドロップ）の部分的復活になる。

### 境界発火時のクリア範囲
- **`placed_order_ids` ＋ `Cart`、`table_number` は残す（採用）** — `Cart` も来店にスコープされる（CONTEXT.md: `Cart` / `来店`）。前客の未確定 Line を残すと、次客がカートバッジの残骸を見る／そのまま注文確定して幽霊注文がキッチンに飛ぶ。`table_number` はタブレットの物理位置なので来店を跨いで有効 — 消すと次客が Welcome 送りになり、スタッフ介入なしで使えなくなって本境界を足した意味が消える。
- **`placed_order_ids` のみ（却下）** — 同じライフサイクルのはずの2つ（イシュー #55 の指摘どおり `Cart` は全く同じ構造）が別の境界を持つ非対称が生まれる。
- **`table_number` も消す（却下）** — 上記のとおり自滅。

### CookieOverflow 対策
- **当日刈り込みのみ（採用）** — `注文状況` 読み出し時に、表示フィルタと同じ「本日の in_store 注文」に絞った id を session へ書き戻す。会計終端導入後の蓄積経路は「終端に達しない注文が滞留したまま日をまたぐ」ケースだけであり、これで配列は「この卓の当日注文数」に抑えられる（数百バイト未満）。
- **件数上限の追加（却下）** — 上限を超えるのは同一卓・同日で数十注文という非現実ケースのみ。切り捨てられた注文が状況から消える新しい事故モードを抱え込む割に実利がない。

## Consequences
- `session[:placed_order_ids]` と `Cart` は**来店スコープ**であることが明文化される（CONTEXT.md: `来店` 新設、`Cart` / `注文状況` に相互参照追記）。
- **ADR-0012 の Consequences「welcome 入口でクリア」を改訂**: リセット経路は二本 — Welcome 再入場（運用上の宣言）＋会計終端（ドメイン境界）。ADR-0012 自体は accepted のまま、本 ADR がライフサイクル記述を上書きする。
- 境界の評価は客 surface の**次の読み出し時**（`注文状況` のポーリング含む）。客が status を眺めている最中に最後の会計が完了すると一覧はクリアされ空表示になる — 会計を終えた客は退店するため許容。
- **同一客の消失（懸念 #3）は仕様として受容**: Welcome 再通過で自分の進行中注文が `注文状況` から消えるのは、Welcome 再入場＝新来店の宣言（イシュー #41）という意味を守った結果。導線上、客が自力で Welcome に到達することはまずない。`Order` 自体は DB に残り、キッチン／レジの進行には影響しない（見えなくなるだけ）。
- **残存リスク（POC 許容）**: 全注文が `walkout` のみで終端（≥1 `Paid` 不成立）した場合と、walkout が打ち切られるまでの窓では、次客まで前客の注文が残り得る — Welcome 境界に委ねる。会計終端の発火後に `Reopen`（打ち切り解除）が起きても、既にクリアされた session には再出現しない（レジ側の補正であり客タブレットは関知しない）。
- CookieOverflow は当日刈り込みで実用上解消。保存先は cookie セッションのまま（サーバ側セッションストアは導入しない）。
