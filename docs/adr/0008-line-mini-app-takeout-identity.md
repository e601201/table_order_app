# テイクアウトの身元基盤に認証済み LINE ミニアプリを採用（Ready 通知はサービスメッセージ）

`Takeout` の注文経路を LINE ミニアプリ（LIFF）に載せ、**テイクアウトに限り LINE 認証を必須**にする。認証された LINE 身元は新エンティティ **`LineAccount`** として永続化し、`Takeout` の `Order` は必ず1つの `LineAccount` を持つ（`In-store` は決して持たない — `table_number` と対をなす相互排他）。`In-store`（客席タブレット）は従来どおり完全に未認証のまま。これにより (1) 注文の持ち主識別（イシュー #29 の Takeout 側の解消）、(2) `OrderReady` 時の LINE 通知、(3) 注文履歴の閲覧、が成立する。

ミニアプリは**認証済み（verified）として審査を通し、Ready 通知はサービスメッセージで送る**。Checkout（ユーザー操作）時にサービス通知トークンを発行して `Order` に保存し、`In progress → Ready` の遷移で「お作りできました」を**1注文につき1通だけ**送信する。

## Considered Options

### なぜテイクアウトだけログイン必須か

- **LINE 認証必須（採用）** — テイクアウト客は店外にいるため、呼び出し（Ready 通知）には到達可能な宛先が必須。あわせて連番 `:id` で他人の注文が見える #29 の穴を「自分の `LineAccount` の注文だけ」で塞げる。LIFF では LINE アプリ内で開いた時点で実質ログイン済みのため、客に見える摩擦はない。
- **匿名のまま推測不能トークンでガード（却下）** — #29 は塞げるが、通知の宛先と注文履歴が成立しない。
- **会員（Member）概念の導入（却下）** — 認証は `Takeout` フローの属性であってロールではない。`Customer` は1ロールのまま、認証の有無を `Order type` に従属させる（`CONTEXT.md` の `Customer` / `LineAccount` を参照）。

### 通知経路

- **認証済みミニアプリ＋サービスメッセージ（採用）** — 公式アカウントの友だち追加が不要で、注文という操作への後続通知という用途がサービスメッセージの設計意図そのもの。トークンは操作1回につき発行・1年有効・最大5通（送信ごとにトークン値が更新される）。
- **LIFF＋Messaging API push（却下）** — 審査不要で POC のリードタイムは短いが、push は客が公式アカウントを友だち追加していることが条件で、未追加の客に Ready を届けられない。本番志向で審査を先に通す判断をした。審査完了までのリードタイムは受容する。

### 認証境界

- **テイクアウト面は入口から全面必須（採用）** — メニュー閲覧も含めて `LineAccount` セッションの内側。サーバーは takeout モードのカート操作・Checkout を一律に拒否でき、状態が1つで済む。
- **Checkout 時のみ要求（却下）** — 「匿名 takeout カートをログイン後に引き継ぐ」状態遷移を抱えるわりに、LIFF では得るものがない。

## Consequences

- `OrderReady` が**名前のある公開イベントに昇格**する（従来はキッチン内部遷移はすべて無名）。発生は order type を問わず、今日の唯一の購読者は Takeout の LINE 通知。`Pending → In progress` は引き続き無名。
- テイクアウトへの到達経路は LIFF URL のみ。Welcome のテイクアウトリンク（`?order_type=takeout`）は廃止する。`/order` 配下の既存4ページは LIFF WebView 内でそのまま再利用。
- 注文履歴画面は「現在進行中＋過去」を兼ねる（kitchen progress の現在状態を表示、更新はページロード時のスナップショット）。リピート注文と事前オンライン決済は**スコープ外** — 会計は従来どおり店頭で `Served → Paid`（ADR-0001 の二軸と順序は不変）。
- 既存の takeout 行（`LineAccount` なし）はリセット容認とし、バリデーションは「`Takeout` なら `LineAccount` 必須」で一本化する（レガシー条件分岐を残さない）。
- 開発中から実 LIFF を接続する（モックログイン環境は作らない）。自動テストに限り ID トークン検証とサービスメッセージ送信をスタブする。
- In-store 注文の持ち主ガードは未解決のまま残る（#29 の In-store 側は本 ADR のスコープ外）。
