# 商品在庫・売り切れ・補充（MenuItem に nullable `stock` ＋ `suspended`、減算は Checkout、操作は Admin 専有）

`MenuItem` に在庫の概念を導入する。`menu_items` に **nullable な `stock`（整数, ≥0）** と **`suspended`（boolean, NOT NULL, default false）** の2列を足す。`stock` が `nil` の商品は**在庫無制限（追跡しない）**、整数の商品は**追跡**し、`stock == 0` で **売り切れ**（独立フラグではなく `stock` からの派生）。`suspended` は在庫と独立した Admin の手動**販売停止**ゲート。**販売可否 = `!suspended && (stock.nil? || stock > 0)`**。在庫の減算は **Checkout（OrderPlaced）時のみ**で、カートは在庫を予約しない。確定時に在庫不足が判明したら**注文全体を原子的にロールバックしカートへ差し戻す**。在庫操作（在庫数・販売停止・補充）は **Admin 専有**。客向けには売り切れ・販売停止を問わず単一の「売り切れ」バッジで見せ、残数は出さない。

背景: ADR-0004 は availability（売り切れ）ライフサイクルを「別 ADR に委ねる」と明示的に先送りした。その結果、これまで商品を「売らない」状態にする唯一の手段は物理削除であり、一時的な品切れを表現できなかった。本 ADR がその保留を解決する。なお ADR-0010 で導入した打ち切り理由 `out_of_stock` は**既に置かれた注文**を支払いなしで閉じる*事後的*な手段で、本 ADR の `売り切れ` は**新規注文を止める** MenuItem の*事前的*状態 — 両者は補完関係で別概念。

## Considered Options

### 在庫モデル

- **カウント式＋手動販売停止の併存（採用）** — `在庫` という語は数量を含意し、`補充` も「数を戻す」操作として自然。一方で在庫が残っていても止めたい局面（品質問題・提供中止）があるため、在庫数とは独立した手動ゲートも要る。`売り切れ`（`stock==0` の派生）と `販売停止`（手動）の2ゲートを併存させ AND で販売可否を決める。
- **売切フラグのみ（boolean）（却下）** — 最小だが「あと何個」を表現できず、`補充` が単なるフラグ OFF になり在庫の語義に合わない。
- **カウントのみ（手動停止なし）（却下）** — 在庫が残るのに止めたい局面を「在庫を0に手動で書く」で代用させると、後で補充したとき本来の数を失う。

### 追跡範囲 / 粒度

- **オプトイン nullable `stock`（採用）** — ドリンク等の実質無制限品にまで毎日カウントを強制すると運用負荷になる。`nil`＝無制限、整数＝追跡を単一列で表現でき Rails 的にも素直。`track_inventory` boolean ＋非null整数は列が増えるだけで等価なので却下。
- **MenuItem 単位の在庫（採用）** — `stock` は `MenuItem` の1列。Size / Addon は在庫を持たず、減算は対象 MenuItem の Line 数量合計で行う。Size 別在庫（jsonb 各 size に在庫を埋める／正規化）は ADR-0004 が却下した「item 内に閉じた値オブジェクト」方針に反し、減算・バリデーション・Admin 編集を一気に複雑化するため却下。Addon 単位の在庫も同様にスコープ外。

### 減算タイミング

- **Checkout（OrderPlaced）で減算（採用）** — `CONTEXT.md` の「Cart は注文確定まで画面の外に一切影響しない（非予約）」不変条件を維持する唯一の選択。一覧の売り切れ表示は*ソフトな目安*、権威ある判定は Checkout 時。
- **カート追加時に予約（却下）** — Cart を永続化する必要が生じ、上記の非予約不変条件に反する。
- **キッチン調理時に減算（却下）** — 売り越しが起き、判定が遅すぎる。

### 在庫不足時（Checkout）

- **注文全体を拒否しカートへ差し戻し（採用）** — 既存の `checkout` トランザクション内で**原子的な条件付き減算**（`stock >= qty` の行だけ減算し、影響行数で成否を判定）。1行でも不足なら全ロールバックし、カートに戻して行ごとに「残り◯個／売り切れ」を提示、客自身が数量調整 or 削除して再確定。Checkout は客が明示的に押した確定行為であり、確定したはずの注文を黙って欠落させるのは意図と金額に反する。
- **不足行を drop して残りを確定（却下）** — ADR-0004 の「閲覧中の silent drop」と対称だが、確定の瞬間に無言で欠落させるのは不適。
- **残数に自動で切り詰めて確定（却下）** — 客の確認なしに注文内容（金額）が変わる。

### 日次リセット

- **自動リセットなし・手動 running カウンタ（採用）** — `stock` は日付スコープを持たない可変整数。0 まで売れたら Admin が `補充` で戻す（朝の開店儀式）。スケジューラを持ち込まない方針は、ActiveStorage をローカルディスクに置く等の POC インフラ最小思想と整合。
- **真夜中 JST に自動リセット（却下）** — `daily_quota` 別列＋日次ジョブが必要で POC には過剰。**既知の制約**として、本採用案は「毎朝 Admin が補充する」運用を要する。

### 数量上限（オーダー画面のステッパー）

- **静的 `max_quantity` のまま（採用）** — `max_quantity` は在庫非依存の「1注文・1行あたり上限」（暴発防止の商品/UX 制約）であり、在庫と二重定義しない。ステッパーを残在庫で動的に絞らない。上限超過は上記の Checkout 全体拒否で捕捉し、差し戻しメッセージで「残り◯個まで」と**実数を初めて提示**する。
- **残在庫で動的キャップ `min(max_quantity, stock)`（却下）** — 確定前の摩擦は減るが、(1) キャップ値から残数が逆算でき「残数非表示」方針が在庫逼迫時にだけ破れる、(2) 非予約モデルでは隣の客の確定で即座に陳腐化し*偽の精度*を与え予約を匂わせる。残数は「権威ある瞬間（確定時の差し戻し）に1度だけ正直に」出す形に統一する。

### 顧客表示

- **表示を残し操作不可＋単一「売り切れ」バッジ（採用）** — メニューから消さず（`menu-is-truth` 思想／復活時の再出現の不自然さ回避）、グレーアウト＋追加無効、商品詳細は閲覧可。売り切れ・販売停止とも客には同じ「売り切れ」バッジに畳む（`Closed` をどの理由でも「キャンセル」と見せる既存パターンと対称）。残数は出さず**二値**のみ。
- **一覧から完全に隠す（却下）** — 在庫復活時に再出現し「さっきあったのに」となる。
- **カテゴリ内で末尾送り（却下）** — 並び替えロジックの追加に見合わない。
- **残り◯個 / 残りわずかを客に表示（却下）** — 非予約モデルでは表示残数が常に古くなりうる。

### 操作権限

- **Admin 専有（採用）** — `CONTEXT.md` の「Menu は Admin 所有・キッチンは Menu 非関与」というロール境界を壊さない。在庫操作は `/admin/menu_items` 上で行い、発見フローは現状どおり「キッチン→声→Admin が操作」。ロール境界の拡張は後から足せる。
- **Admin ＋ Kitchen（却下）** — 発見地点のエルゴノミクスは良いが、`CONTEXT.md` のキッチン定義変更とそれ自体が境界変更 ADR を要する。当面は純粋性を優先。
- **Admin ＋ Cashier（却下）** — レジは厨房を見ず、在庫の一次情報から遠い。

### Admin 操作 UI

- **一覧クイック操作＋編集フォーム（採用）** — サービス中の速度のため、`/admin/menu_items` 一覧に「売切⇄再開（補充）」トグルと在庫ステッパーを置き、重いフォーム全体を再送しない軽量ルート（`PATCH /admin/menu_items/:id/availability`）で即時反映。在庫数・`suspended` の恒久設定は編集フォームでも可。補充は**絶対値セット**（冪等で誤操作に強い）。
- **編集フォームのみ（却下）** — 追加ルートなしで最小だが、サービス中に画像・sizes・addons を含む重いフォームを再送する羽目になる。

## Consequences

- マイグレーション: `menu_items` に `stock`（integer, null 許容）と `suspended`（boolean, NOT NULL, default false）を追加。バリデーション: `stock` は present のとき 0 以上の整数。
- 派生ヘルパー: `sold_out?`（`stock == 0`）、`sellable?`（`!suspended && (stock.nil? || stock.positive?)`）。`売り切れ` は列ではなく `stock` からの計算。
- `as_customer_json` に `sellable`（または `sold_out`）の真偽を足す。**残数は送らない**。顧客一覧/詳細は二値で描画し、追加ボタンを無効化。
- ガードは3層: `add_to_cart` で販売不可品を拒否（早期失敗）、`cart_review` でカート内の在庫切れ行を事前警告、**Checkout が権威ある最終判定**。
- `checkout`: 既存 `Order.transaction` 内で追跡品のみ原子的条件付き減算（`UPDATE ... SET stock = stock - qty WHERE id = ? AND stock >= qty`、影響行数で判定）。`nil`（無制限）は減算しない。1行でも不足→全ロールバック→カート差し戻し＋行別メッセージ。
- 確定済み `Order` / `OrderItem` はスナップショット（name / price / size / addons）のため、後の在庫・販売停止変更の影響を受けない。キッチン進行・`/admin/orders`（ADR-0005 閲覧専用のまま）にも無影響。
- ADR-0010 の打ち切り理由 `out_of_stock` と**共存**: `売り切れ` は新規注文を止める*予防的*な MenuItem 状態、`out_of_stock` closure は*既に置かれた*注文を閉じる事後手段。無制限品（`nil`）が物理的に切れた場合や、在庫追跡品でも提供直前に作れなくなった場合は、従来どおり closure 側で処理する。
- 操作は **Admin 専有**: `/admin/menu_items` 一覧のクイックトグル＋ステッパー、軽量ルート `PATCH /admin/menu_items/:id/availability`、編集フォームでの恒久設定。補充は絶対値セット。`CONTEXT.md` のロール定義は不変（Admin の Menu 所有に在庫操作を内包する一文を追記済み）。
- **既知の制約**: 自動リセットがないため、毎朝 Admin が在庫を補充する運用を要する。

## 非ゴール

Size 別在庫 / Addon 在庫 / 真夜中 JST の自動リセット（`daily_quota`）/ 低在庫ダッシュボード / Kitchen・Cashier への操作権限拡張 / 顧客への残数表示 / 数量ステッパーの動的キャップ。いずれも後続で状態モデルに触れず追加できる。
